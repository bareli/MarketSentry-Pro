## Summary

`services.py` already exposes `marketsentry.search_instruments` as "usable from Assist/LLM
tooling" per README's Services section, but there's no actual conversation intent wired up for a
natural "what's Bitcoin trading at" voice query - today that would require the user (or an LLM
agent with tool access) to know to call the service explicitly.

## Recommended change

Register a small `conversation` intent (or confirm the existing service's LLM-tool exposure already
covers this adequately via Assist's own tool-calling, in which case this closes as "already true,
no new code needed" - needs a live check against a real Assist/LLM-configured HA instance before
assuming new code is required).

## Relevant files

- `custom_components/marketsentry/services.py` (`search_instruments`, already exposed)
- Possibly a new `conversation.py` if a dedicated intent is needed beyond the existing service

## Implementation (2026-11-01, qa-developer)

**Mechanism chosen:** a custom `homeassistant.helpers.intent.IntentHandler`
(`SearchInstrumentsIntentHandler` in new `custom_components/marketsentry/intent.py`),
registered via `intent.async_register(hass, ...)` from `async_setup()` in `__init__.py`
(domain-wide, once - same place the WS command is registered).

**Why not a custom `llm.API`/`llm.async_register_api`, as the brief suggested
investigating:** reading the installed `homeassistant` package
(`homeassistant/helpers/llm.py`, this dev machine's HA version) showed
`llm.async_register_api` registers a whole competing `llm.API` - a full
replacement tool/prompt bundle a conversation agent must be configured to use
*instead of* the built-in `"assist"` API (`LLM_API_ASSIST`/`AssistAPI`). That's a much
bigger surface than exposing one action, and not how any core integration adds a
single tool. The actual extension point `AssistAPI` uses internally
(`AssistAPI._async_get_tools`) is: every `intent.IntentHandler` registered via
`homeassistant.helpers.intent.async_register` whose `platforms` matches the
exposed-entity domains gets auto-wrapped in an `llm.IntentTool` and exposed to
Assist voice and any LLM-tool-calling conversation agent configured to use the
Assist API - the same mechanism every built-in `Hass*` intent uses. That is the
smallest-correct, in-HA-maintained path, so this change registers an intent
instead of a custom API.

**Reuse, not duplication:** the provider-search/credential lookup logic was
extracted from `services.py`'s `handle_search_instruments` into a new shared
`async_search_instruments(hass, provider_key, query, limit)` function. Both the
`search_instruments` service (unchanged behavior/schema for script/automation
callers) and the new intent handler call it; only the HA-facing call path
(`ServiceCall` + dict response vs. `Intent`/`IntentResponse` with a spoken-speech
summary) differs.

**Scope note on "what's Bitcoin trading at":** `search_instruments`
(and `InstrumentRef`) returns matching instrument metadata only - no live price
field - so the intent's speech names the matches it found (e.g. "Found Bitcoin
(BTC).") rather than quoting a price; adding a live-quote fetch would be new
behavior beyond `search_instruments` itself and was out of this issue's stated
scope (no changes to the existing service's behavior).

**manifest.json:** no new dependency added. `homeassistant.helpers.intent` is a
plain helper module (writes to `hass.data`), not a component - registering an
intent needs no `"dependencies"` entry, and no `homeassistant.components.*`
import was added to the integration.

**Files changed:** `custom_components/marketsentry/intent.py` (new),
`custom_components/marketsentry/services.py` (extracted
`async_search_instruments`, no behavior change), `custom_components/marketsentry/__init__.py`
(registers the intent in `async_setup`), `tests/test_intent.py` (new, 6 tests).
