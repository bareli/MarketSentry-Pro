## Summary

`D-003` (`team/decisions.md`) decided two changes together for UX-003's lopsided-digest finding:
truncate long instrument names (~60 chars) **and** prefer the device name over the full
`friendly_name`. Only the truncation landed (`daily_digest.yaml` now pipes
`friendly_name | truncate(60, True, '…')`), confirmed correct and verified by qa-ux-expert. The
device-name half was explicitly out of scope in the fixer's handback and is still missing: a
Polymarket line still carries whatever suffix is baked into its sensor's `friendly_name` (e.g. "...
Probability"), just capped at 60 chars, rather than reading as the clean device name.

Splitting this out rather than reopening UX-003 (#6, closed) because the truncation alone already
fixes the actual complaint D-003's own reasoning named: "a 5x-longer line defeats [glanceability]
for an owner who does track Polymarket" — that's resolved. This is a further polish, not an
unresolved defect.

## Expected

A digest line for a Polymarket outcome reads using the device's plain name (the way the HA device
registry already stores it, same source the card uses), not the sensor's possibly-longer
`friendly_name` with its entity-type suffix, before truncation is even applied.

## Actual

The digest line still uses `s.attributes.friendly_name` directly (truncated to 60 chars), which
HA's own `friendly_name` convention tends to append the entity's own descriptive suffix to the
device name for a sensor's display name.

## Relevant files

- `blueprints/automation/marketsentry/daily_digest.yaml` (the `variables.digest` Jinja template,
  `integration_entities('marketsentry')`/`expand()` loop).

## Recommended remediation

Within the same Jinja loop, prefer `state_attr(s.entity_id, 'device_id')`'s device name if
reachable from a blueprint template (HA's `device_attr(entity_id, 'name')` Jinja function, if
available in this HA version) over `s.attributes.friendly_name`, falling back to `friendly_name`
if the device lookup fails for any reason. Needs a live HA instance to confirm `device_attr`'s
exact behavior/availability before implementing - flag that constraint when this is picked up.

## Regression test

None yet - no automated blueprint-template test harness exists in this repo (same gap noted for
BUG-004/UX-002/UX-003's own verification, all hand-traced rather than executed).

## Implementation (2026-10-31, owner asked to implement now)

`daily_digest.yaml`'s digest line now reads:

```jinja
{{ (device_name(s.entity_id) or s.attributes.friendly_name) | truncate(60, True, '…') }}: {{ s.state }}...
```

Used HA's real `device_name(lookup_value)` Jinja global
(`homeassistant/helpers/template/extensions/devices.py`), not `device_attr(entity_id, 'name')` as
originally recommended above - `device_name()` already does `device.name_by_user or device.name`
internally (prefers an owner rename over the auto-generated name), which `device_attr(..., 'name')`
does not, and it returns `None` cleanly for an entity with no device or no match, same fallback
shape the original recommendation asked for. Confirmed the function exists and its signature/
behavior by reading the installed `homeassistant` package directly (no live HA instance needed to
settle the "is `device_attr` available" open question - it's a real, requires-`hass`,
non-`limited_ok` template global, available in a normal automation template context).
