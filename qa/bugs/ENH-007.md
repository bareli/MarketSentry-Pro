## Summary

README's own Limitations section already names this: "the 'stream connected' binary sensor is an
approximation of 'the stream task is running,' not a live up/down signal." Each provider's
`stream()` loop handles its own reconnect/backoff internally without reporting intermediate
transitions, so a provider that is silently reconnecting in a tight loop (bad credentials that
pass initial auth, a flaky network) still reads as "connected" the whole time.

## Recommended change

Have each provider's `stream()` loop report its actual connection phase (connecting / connected /
reconnecting / backing off) through a small callback or shared state object the coordinator
already owns, and surface that as the binary sensor's real state plus a `reconnect_count`
attribute, instead of inferring "connected" from "the asyncio task hasn't died."

## Implementation (2026-11-01, qa-developer)

**D-034's open question, resolved:** attribute-level, not a new state. `reconnecting` is a plain
`bool` attribute on the existing `binary_sensor.stream_connected` entity, alongside a
`reconnect_count` `int` attribute - no new entity domain/platform, and the on/off contract stays
exactly two values. The change in meaning (see below) is deliberate and is what the issue asked for.

**Mechanism:** a `StreamStatus` dataclass (`phase: Literal["connecting", "connected",
"reconnecting", "backing_off", "stopped"]`, `reconnect_count: int`) in `providers/base.py`, plus an
`OnStreamStatus = Callable[[StreamStatus], None]` sync callback type. `Provider.stream()`'s
signature grew one new trailing optional parameter, `on_status: OnStreamStatus | None = None`
(default `None`, so every existing caller/override keeps compiling under `mypy --strict`).

- `providers/finnhub.py` / `providers/alpaca.py`: the existing `while True` reconnect/backoff loop
  in `stream()` now calls `on_status` at each transition it was already making internally -
  "connecting" before the very first attempt, "reconnecting" before every retry, "backing_off"
  right after a failed attempt (before the `asyncio.sleep` backoff delay), and "connected" from
  inside `_connect_and_listen` once the socket is open (Finnhub) / once WS auth actually succeeds
  (Alpaca - a bare socket open is not "connected" for Alpaca, since unauthenticated sockets get
  closed by the server). `reconnect_count` is a separate counter from the existing backoff
  `attempt` counter: `attempt` resets to 0 on a successful connect (so backoff delay shortens
  again), `reconnect_count` never resets - it is a running total of how many times this stream
  task has had to recover, which is what the sensor attribute reports. No other change to either
  provider's reconnect/backoff timing or control flow.
- `providers/polymarket.py`: `supports_streaming = True` there too, via its own `ws.py`
  `PolymarketWsManager` - the issue text's "Polymarket/FX/CoinGecko are poll-only, don't touch
  them" framing was itself wrong for Polymarket.
- `__init__.py`'s `_async_start_streaming`: builds one `on_status` closure per entry that updates
  three `MarketSentryRuntimeData` fields (`stream_phase`, `stream_reconnect_count`, and
  `stream_connected = phase == "connected"`) and re-dispatches the full `StreamStatus` object on
  the existing `SIGNAL_STREAM_STATE_<entry_id>` signal (previously a bare `bool`). `stream_connected`
  is kept as a field (diagnostics.py and the sensor both still read it) but is now derived from the
  real phase instead of "the task hasn't died yet" - it is only `True` while actually connected, and
  briefly flips `False` during a live reconnect, which is the whole point of the fix. The `finally`
  block (task cancelled on unload, or an unhandled bug) reports a `"stopped"` phase - a value
  `on_status` callers can see but providers themselves never emit.
- `binary_sensor.py`'s `StreamConnectedBinarySensor`: `is_on` is unchanged in shape (still reads
  `runtime_data.stream_connected`, still a plain bool) but now means "really connected right now",
  not "task alive". Added `extra_state_attributes` -> `{"reconnecting": phase in
  {"reconnecting", "backing_off"}, "reconnect_count": int}`.
- `diagnostics.py`: added `stream_phase` / `stream_reconnect_count` next to the existing
  `stream_connected` key (additive, nothing removed).
- `README.md`'s Limitations bullet updated to describe the new live reporting instead of the old
  "approximation" caveat.

## Bug found and fixed during review (qa-manager, before merge)

The handed-back diff gave `polymarket.py`'s `stream()` an `on_status` parameter it accepted but
never called - a real regression, not a no-op: `__init__.py`'s `_async_start_streaming` now starts
every entry at `stream_phase="connecting"`/`stream_connected=False` and only flips to `"connected"`
when the provider itself calls `on_status`. Since Polymarket's override never did, its binary
sensor would have gone from today's working "on while the task is alive" to **permanently off**,
for the one provider (besides Finnhub/Alpaca) that genuinely streams live. The brief's "Polymarket
is poll-only, don't touch it" premise (inherited from the issue text) was simply wrong.

Fixed properly rather than papering over it with a fake always-"connected" stub: `ws.py`'s
`PolymarketWsManager` already has its own `on_connection_state_change(bool)` hook for exactly this
(exponential-backoff reconnects) - it was just never wired to anything. `polymarket.py`'s `stream()`
now passes a callback that translates that `bool` into a `StreamStatus` (`"connected"` on `True`,
`"reconnecting"` on `False`), with a locally-tracked `reconnect_count` that increments on every
reconnect after the first successful connect (independent of `ws.py`'s own `_reconnect_attempt`,
which has different reset semantics and isn't exposed). Added
`tests/providers/test_polymarket.py::test_stream_reports_connect_and_reconnect_via_on_status`
(monkeypatches `PolymarketWsManager` with a fake that exposes the captured callback, drives
connect/disconnect/reconnect, asserts the exact `StreamStatus` sequence and `reconnect_count`).
Confirmed this test fails against the handed-back pre-fix code (asserts `"connected"` appears
without ever being emitted) and passes with the fix. Full suite re-run clean: 199 passed (was 198
in the original hand-back, +1 for this test).

**Backward compatibility:** anyone templating on the raw state string still gets exactly `"on"`/
`"off"` (HA's binary_sensor domain), never a third value. The one real behavior change - `is_on`
can now read `False` while the task is alive but reconnecting, where before it stayed `True` the
whole time - is the defect this issue describes, not a new one; it only differs from before during
an actual reconnect/backoff window, which was exactly the undetectable case the record names.

**Files changed:** `custom_components/marketsentry/providers/base.py`,
`providers/finnhub.py`, `providers/alpaca.py`, `providers/polymarket.py` (real wiring, see review
note above - not signature-only), `custom_components/marketsentry/__init__.py`, `binary_sensor.py`,
`diagnostics.py`, `README.md`.

**Tests added:** `tests/providers/test_finnhub.py` (+2: `_connect_and_listen` reports "connected"
with the given `reconnect_count`; `stream()`'s loop reports connecting -> backing_off ->
reconnecting with a rising `reconnect_count`), `tests/providers/test_alpaca.py` (+3: same
"connected" case gated on auth succeeding, not just the socket opening; a failed auth reports no
status at all; the same connecting/backing_off/reconnecting loop sequence),
`tests/providers/test_polymarket.py` (+1: connect/reconnect via `on_connection_state_change`, added
during review), and a new `tests/test_binary_sensor.py` (+5: `is_on` false while
connecting/reconnecting even though the "task alive" proxy would have read true; true only once
actually connected; `reconnecting`/`reconnect_count` attribute values for each phase).

**Failing-first proof:** copied the new test files into a `git worktree add --detach` checkout at
baseline commit `906af14` (pre-fix) and ran them there with
`pytest tests/providers/test_finnhub.py tests/providers/test_alpaca.py tests/test_binary_sensor.py
-p no:homeassistant`: the two provider files failed to collect (`ImportError: cannot import name
'StreamStatus'`), and 4 of 5 `test_binary_sensor.py` cases failed (`extra_state_attributes` was
`None` - the attribute didn't exist yet). Removed that worktree afterward. The Polymarket test's

fix; the full Windows-safe suite (`ruff check`, `mypy --strict`, `pytest tests
--ignore=tests/config_flow -p no:homeassistant`) is green at 199 passed (was 188 before this fix).
