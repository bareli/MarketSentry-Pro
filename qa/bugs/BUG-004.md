## Summary

`BP-02` requires the light-flash and TTS branches in `resolved_announce.yaml` to be "optional and
independently skippable." They are not: the blueprint's `action` conditions test the raw input
names `flash_light`, `tts_entity` and `tts_target` as if they were Jinja variables
(`"{{ flash_light is not none and flash_light != [] }}"`, etc.), but those names are never bound -
Home Assistant's blueprint `!input` substitution (`annotatedyaml.input.substitute`) only replaces a
YAML node that **is** an `Input` placeholder (i.e. `!input foo` as the whole node); it does not
expose input names as template variables inside a plain string, and the blueprint's own
`variables:` block only defines `outcome_name` and `winning_outcome`. At render time
`flash_light`/`tts_entity`/`tts_target` are therefore Jinja `Undefined` objects, and `Undefined`'s
`__eq__`/`__ne__` only compare equal to another `Undefined` of the same type - so `!= []`,
`not in [none, '']` and `is not none` all evaluate `True` regardless of what the user actually
configured. Both conditions are unconditionally `True`. For the light branch this is a mostly
harmless no-op (`light.turn_on` with an empty `target` does nothing), but for the TTS branch - whose
description explicitly says "Leave empty to skip the spoken announcement" and whose **default is
empty** - the automation will still call `tts.speak` with `entity_id: ""` on every resolution
event, which is not a valid entity id. This breaks the blueprint's advertised default behaviour (no
TTS configured) for every user who uses it as documented.

## Steps to reproduce

1. Read `blueprints/automation/marketsentry/resolved_announce.yaml`: `variables:` only declares
   `outcome_name`/`winning_outcome`; `flash_light`/`tts_entity`/`tts_target` are referenced directly
   in two `value_template` conditions without ever being substituted or declared as variables.
2. Confirm HA's substitution is literal-node-only:
   `annotatedyaml/input.py::substitute()` - `if isinstance(obj, Input): ... return substitutions[obj.name]`,
   else recurses through list/dict and returns a bare `str` unchanged.
3. Reproduce the exact Jinja evaluation HA would perform, with the same `Undefined` type HA uses
   (`jinja2.Undefined`, which HA's `LoggingUndefined` subclasses without touching `__eq__`/`__ne__`):
   ```python
   import jinja2
   env = jinja2.Environment(undefined=jinja2.Undefined)
   env.from_string('{{ flash_light is not none and flash_light != [] }}').render()          # -> 'True'
   env.from_string("{{ tts_entity not in [none, ''] and tts_target is not none and tts_target != [] }}").render()  # -> 'True'
   ```

## Expected

With the blueprint's own defaults (`flash_light: []`, `tts_target: []`, `tts_entity: ""` - i.e. the
user configures only the required trigger), both conditions should evaluate `False` and neither
`light.turn_on` nor `tts.speak` should run.

## Actual

Both conditions evaluate `True` unconditionally (confirmed above), independent of what the user
configured. With the defaults, `tts.speak` is still invoked with `entity_id: ""`.

## Evidence

```
$ python -c "
import jinja2
env = jinja2.Environment(undefined=jinja2.Undefined)
t1 = env.from_string('{{ flash_light is not none and flash_light != [] }}')
print('light condition (flash_light undefined):', t1.render())
t2 = env.from_string(\"{{ tts_entity not in [none, ''] and tts_target is not none and tts_target != [] }}\")
print('tts condition (tts_entity/tts_target undefined):', t2.render())
"
light condition (flash_light undefined): True
tts condition (tts_entity/tts_target undefined): True
```
Also confirmed by reading `jinja2/runtime.py`'s `Undefined.__eq__`/`__ne__`
(`return type(self) is type(other)`) and HA's `LoggingUndefined` (overrides only
`__str__`/`__iter__`/`__bool__`, not `__eq__`/`__ne__`), and HA's
`homeassistant.components.blueprint.models.BlueprintInputs.async_substitute` ->
`annotatedyaml.input.substitute`, which only replaces literal `Input` nodes.

## Likely root cause

The author intended `flash_light`/`tts_entity`/`tts_target` to be usable inside the condition
templates the same way `trigger` is automatically available in action templates, but blueprint
inputs are not auto-exposed as template variables - they must be either referenced with `!input` at
the exact YAML node that needs the value, or explicitly copied into the `variables:` block (e.g.
`variables: { flash_light: !input flash_light, ... }`) before a template can read them by name.
Proven by source inspection of HA's substitution mechanism and Jinja's `Undefined` semantics above;
this is a root cause, not a guess - the only thing not independently exercised is an actual running
HA automation engine (out of scope this session per the brief - no live HA instance access).

## Relevant files

- `blueprints/automation/marketsentry/resolved_announce.yaml` (`variables:` block and both
  `action[].if[].condition.value_template` entries)

## Recommended remediation

Add `flash_light`, `tts_target` and `tts_entity` to the blueprint's `variables:` block via `!input`
substitution (e.g. `flash_light: !input flash_light`) so they are bound as real Jinja variables
before the `if` conditions reference them - this is the standard fix pattern used by HA's own
official blueprints for optional inputs gated by a condition.
