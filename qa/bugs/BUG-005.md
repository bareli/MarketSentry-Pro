## Summary

DET-07 asks to confirm `OfficialRatePublishedDetector` doesn't also fire for Frankfurter-sourced fx
instruments, where "official rate" doesn't apply (README's automation example and the event's own
name are specifically about the Bank of Israel's published representative rate). It does fire for
both: `_build_detectors(kind, opts)` only receives the instrument **kind** ("fx"), never the
specific `InstrumentRef`/id, so it cannot and does not distinguish a `"boi:EUR:ILS"` ref from a
`"frankfurter:EUR:ILS"` ref - every fx tracker gets an `OfficialRatePublishedDetector` wired. The
call site, `__init__.py`'s `_async_process_quote`, is equally unconditional: `if
tracker.detectors.official_rate_published is not None: events +=
tracker.detectors.official_rate_published.check(..., published_date=(quote.ts or now).date())` -
no check anywhere on `tracker.ref.id`'s source prefix. Because `fx.py`'s `_frankfurter_quote()`
sets `Quote.ts` from Frankfurter's own `date` response field (which changes once per calendar day,
same shape as BOI's `TIME_PERIOD`), a Frankfurter market-rate instrument's `published_date` also
changes once a day - so the detector will fire `marketsentry_official_rate_published` for it too,
one day after the first observation, exactly like a real BOI instrument. A user who built an
automation on this event type assuming "official BOI rate" will also get it for a plain market-mid
Frankfurter instrument.

## Steps to reproduce

1. `python -c "import custom_components.marketsentry as m; from custom_components.marketsentry.const import default_options_for_kind; d = m._build_detectors('fx', default_options_for_kind('fx')); print(d.official_rate_published is not None)"` → `True`, for the generic "fx" kind with no source distinction possible.
2. Read `custom_components/marketsentry/__init__.py` lines ~359-362 (`_async_process_quote`): the
   `official_rate_published` branch is gated only on `tracker.detectors.official_rate_published is
   not None`, never on `tracker.ref.id` / `tracker.ref.extra` to check whether the ref is
   `"boi:..."` vs `"frankfurter:..."`.
3. Read `custom_components/marketsentry/providers/fx.py`'s `_frankfurter_quote()`: `date_str =
   data.get("date")` from Frankfurter's own response, which changes daily - the same kind of
   date-transition signal `OfficialRatePublishedDetector.check()` is designed to fire on.

## Expected

Per DET-07 and the feature's own documented intent (README's automation example, the event name
itself), `official_rate_published` should fire only for Bank-of-Israel-sourced fx instruments
(`ref.id` starting with `"boi:"`), never for Frankfurter-sourced ones.

## Actual

The detector is wired and invoked identically for both sources; a Frankfurter instrument's quote
date transition fires the same bus event a BOI instrument's would.

## Likely root cause

`_build_detectors(kind: str, opts: dict) -> InstrumentDetectors` only ever sees the instrument
*kind*, not the specific ref, so a per-source distinction within "fx" is structurally impossible at
that layer; the fix has to happen either by adding a source check or by passing the ref (or at
least `ref.id`/a `source` flag) into `_build_detectors`, or by gating the `_async_process_quote`
call site on `tracker.ref.id.startswith("boi:")`. Proven by direct execution + code reading above;
not a guess.

## Relevant files

- `custom_components/marketsentry/__init__.py` (`_build_detectors`, `_async_process_quote`)
- `custom_components/marketsentry/providers/fx.py` (`_frankfurter_quote`'s `date` field vs
  `_boi_quote`'s `TIME_PERIOD` field - both feed `Quote.ts`, both look identical to the detector)

## Recommended remediation

Gate the `official_rate_published` call in `_async_process_quote` on the ref's source, e.g.:
```python
source, _base, _quote = tracker.ref.id.split(":")
if tracker.detectors.official_rate_published is not None and source == "boi":
    events += tracker.detectors.official_rate_published.check(...)
```
(mirrors the existing `source == "boi"` check pattern already used in `sensor.py`'s `RateSensor`).
Simpler than threading a new parameter through `_build_detectors`.
