## Summary

`MarketSentryInstrumentCard.getStubConfig(hass)` returns `{ type: "...", entity: "" }` when the
account has zero tracked instruments yet (`buildRows(hass)[0]?.entityId || ""`). Passing that
exact config straight into the same class's own `setConfig()` throws synchronously
(`'entity' is required`), instead of rendering the card's own existing graceful "entity not
found" placeholder. This is the first-run path: a brand-new HACS install with no instrument added
yet, where a user opens a dashboard's card picker and picks "MarketSentry Pro Instrument" before
adding anything in Settings - exactly the moment a friendly placeholder matters most.

## Steps to reproduce

1. In the Playwright harness (or any HA frontend with the bundle loaded), build a `hass` object
   with no MarketSentry Pro entities (`entities: {}, states: {}, devices: {}`).
2. Call `MarketSentryInstrumentCard.getStubConfig(hass)` - returns `{ type: "custom:marketsentry-instrument-card", entity: "" }`.
3. Create an element and call `el.setConfig(stub)`.

## Expected

The card already implements a graceful placeholder for exactly this situation - `_render()`'s
`row ? this._renderBody(row, lang) : ...t(lang, "empty_instrument", { entity: this._config.entity })` -
so with no matching entity it should render `"Entity not found or not a MarketSentry Pro
instrument: "` (empty entity name), the same as the card already does for any other unmatched
`entity` string once `setConfig` succeeds.

## Actual

`setConfig()` throws before `_render()` is ever reached:

```
Error: marketsentry-instrument-card: 'entity' is required
```

Reproduced directly in the browser (Playwright, Chromium) against the real built bundle:

```json
{
  "stub": { "type": "custom:marketsentry-instrument-card", "entity": "" },
  "threw": true,
  "message": "marketsentry-instrument-card: 'entity' is required"
}
```

In a real Lovelace card picker, `setConfig` throwing on the stub config is normally caught by HA
and rendered as a generic "Error rendering card" box rather than crashing the dashboard - but that
still means a first-time user who tries the card before adding an instrument sees a raw JS error
message instead of the friendly "no instrument yet, go add one" UI the component already has code
for.

## Likely root cause

`card/src/marketsentry-instrument-card.js`, `setConfig()`:

```js
setConfig(config) {
  if (!config.entity) {
    throw new Error("marketsentry-instrument-card: 'entity' is required");
  }
  ...
```

treats an empty-string `entity` as a configuration error, but `getStubConfig()` (same file)
deliberately produces an empty-string `entity` for exactly the case where no instrument exists
yet to default to. The two pieces of code disagree about what an empty `entity` means.

## Relevant files

- `card/src/marketsentry-instrument-card.js` (`getStubConfig`, `setConfig`, `_render`'s
  `empty_instrument` branch)
- `card/src/i18n.js` (`empty_instrument` string, all 8 languages - already fit for this purpose,
  just unreachable via the stub path)

## Recommended remediation

In `setConfig()`, only throw when `config.entity` is `undefined`/missing entirely (a genuinely
malformed YAML config), and accept an explicit empty string as "no entity selected yet" so it
falls through to the existing `empty_instrument` placeholder. Alternatively, have
`getStubConfig()` omit the `entity` key entirely when there are no rows, if `setConfig` should
keep rejecting an explicit empty string - either fixes the disagreement, the first is smaller.
