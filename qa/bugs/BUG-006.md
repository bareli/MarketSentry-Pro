## Summary

While performing the owner-requested post-batch live HACS update to v0.11.0 (ENH-007/013/015/018),
the dashboard took far longer than any previous update to finish loading after the required
restart. `/config` pages (Integrations, Logs) loaded fine and fast throughout, which pointed away
from the backend being generally down and toward a specific slow/failing step. Searching the system
log for "marketsentry" during the stuck window turned up a real exception, confirmed live:

```
Exception in <function _async_process_intent at 0x...> when processing platform 'intent':
(<HomeAssistant NOT_RUNNING>, 'marketsentry', <module 'custom_components.marketsentry.intent'
from '/config/custom_components/marketsentry/intent.py'>)
Traceback (most recent call last):
  File ".../homeassistant/components/intent/__init__.py", line 643, in _async_process_intent
    await platform.async_setup_intents(hass)
TypeError: 'NoneType' object can't be awaited
```

## Root cause

ENH-015 added `custom_components/marketsentry/intent.py` with a **plain `def async_setup_intents
(hass) -> None`**, manually called (synchronously, not awaited) from `__init__.py`'s `async_setup()`.
That manual call worked fine and was what the unit tests (`tests/test_intent.py`) exercised - which
is exactly why this passed CI and local verification.

What neither the implementation nor its review caught: a module named `intent.py` exposing a
top-level function named `async_setup_intents` is *also* HA core's own documented integration-platform
extension point - confirmed by reading the installed `homeassistant.components.intent` package
directly:

```python
class IntentPlatformProtocol(Protocol):
    """Define the format that intent platforms can have."""
    async def async_setup_intents(self, hass: HomeAssistant) -> None:
        """Set up platform intents."""

async def _async_process_intent(hass, domain, platform: IntentPlatformProtocol) -> None:
    await platform.async_setup_intents(hass)
```

`homeassistant.components.intent`'s own `async_setup` calls `async_process_integration_platforms
(hass, DOMAIN, _async_process_intent)`, which auto-discovers every loaded integration's `<domain>.intent`
module and `await`s its `async_setup_intents(hass)` - completely independent of, and in addition to,
our own manual call. Since ours was a plain (non-async) function, `platform.async_setup_intents(hass)`
ran synchronously and returned `None`; HA's `await None` then raised the `TypeError` above. This is a
real exception on **every** real HA startup with this version installed, not a test artifact - the
existing unit tests never exercised this path since they call `async_setup_intents` directly rather
than through HA's own bootstrap-time platform discovery (the exact class of gap `qa/CLAUDE.md` warns
about for anything `config_flow`/bootstrap-shaped that only a full `hass` fixture - or, as here, a
real live instance - exercises).

## Fix

- `intent.py`: `async_setup_intents` is now `async def` (it was already a no-op coroutine candidate -
  the body does nothing async, but HA's own protocol requires a real coroutine function so `await`
  works). Docstring explains why, citing the real `IntentPlatformProtocol`.
- `__init__.py`: removed the manual `from .intent import async_setup_intents` + `async_setup_intents
  (hass)` call from `async_setup()`. HA's own auto-discovery now calls it exactly once; keeping a
  manual call too would be redundant (harmless given the function's own idempotency guard, but
  pointless) and was the thing that made the broken sync signature "work" locally in the first place.
- `tests/test_intent.py`: the two existing `async_setup_intents` tests are now `async def` and
  `await` the call (they were silently testing a now-impossible-to-reach code shape before - calling
  a sync function without awaiting it never would have caught this). Added
  `test_async_setup_intents_is_a_coroutine_function`, asserting
  `inspect.iscoroutinefunction(async_setup_intents)` directly - the exact property whose absence
  caused the live crash, so this regression can't silently return.

## Verification

Full Windows-safe suite after the fix: `ruff check` clean, `mypy --strict` clean (26 files), `pytest
tests --ignore=tests/config_flow -p no:homeassistant -q` -> 211 passed (was 210, +1 new test).

**Live re-verification (2026-11-01, qa-manager):** redeployed v0.11.1 to the owner's real instance
via HACS Redownload + full restart (same gated `live`-environment procedure as the rest of this
batch). Searched `/config/logs` for "marketsentry" after the restart settled: only the pre-existing,
unrelated `Volume24hrSensor` state_class warning remains - no `async_setup_intents`/`TypeError`
exception this time. Confirmed `/config/integrations/integration/marketsentry` shows "Version
0.11.1" and the `AAPL` device's `Price` sensor reads a live value ($164.63), same as before the
restart - the fix did not regress anything else. This is the actual regression test for this bug:
the original failure was only observable through a real HA bootstrap, which is exactly what this
re-verification exercised.
