## Summary

The notify-oriented blueprints send a flat `notify.mobile_app_*` message today. HA's mobile app
notify platform supports actionable notification buttons (snooze, open a specific dashboard view,
dismiss and don't alert again for N hours) via the `data.actions` payload - unused here, so every
alert is a plain read-and-swipe-away notification with no quick response.

## Recommended change

Add an optional `data.actions` block (behind a new blueprint input, default off to avoid changing
existing automations' behaviour) offering at least "open dashboard" and "snooze this instrument for
1 hour" - the snooze would need a small `input_boolean`/timer per instrument or a shared cooldown
override, which is the real design question here.

## Implementation (2026-10-31, D-032)

D-032 narrowed the snooze design: a per-automation `input_boolean` helper the user creates once,
not new backend state. Both blueprints gained `mobile_notify_target`/`snooze_hours`/`snooze_helper`
inputs (all optional, defaulting to today's exact unconfigured behavior), an "Open dashboard"
action button (reusing the existing `/config/integrations/integration/marketsentry` link
convention from BUG-002/ENH-002), and a second trigger reacting to the Snooze button's
`mobile_app_notification_action` event to turn the helper on, delay, then off.

**Bug found and fixed during review (qa-manager, before merge):** the original `trigger:` list
wrapped `!input market_trigger` (which resolves to a LIST per HA's `selector: trigger: {}`) as a
bare list item alongside the new snooze trigger, producing a list-within-a-list that fails HA's
real `cv.TRIGGER_SCHEMA` (`MultipleInvalid: expected a dictionary @ data[0]`) - confirmed by running
the actual substituted structure through the installed `homeassistant.helpers.config_validation`
module. This would have broken every automation built from either blueprint, since `market_trigger`
is a required input - not a theoretical edge case. Fixed by wrapping in `{"triggers": [...]}`, HA's
own documented nested-trigger-group syntax (`cv._base_trigger_list_flatten` is built to unwrap
exactly this). Added `tests/blueprints/test_trigger_schema.py` - the existing harness only exercises
Jinja templates, not trigger-config structural validity, which is why this class of bug wasn't
caught by the 18 tests that already passed. Commit `b8398e9`.
