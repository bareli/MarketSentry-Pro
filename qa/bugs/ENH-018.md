## Summary

Current coverage is Polymarket (outcomes), Finnhub/Alpaca (stocks), Frankfurter/Bank-of-Israel (FX),
CoinGecko (crypto). `qa/knowledge/historical-risk-areas.md` already flags "new instrument kind /
new provider" as this codebase's highest-risk change shape, and CoinGecko's rate limit under
sustained load is noted there as genuinely unverified. A new provider (another FX source for
redundancy, a second crypto exchange, or a new `commodity` kind for gold/oil/futures) is worth
planning deliberately against that known risk rather than rushed.

## Recommended change

Pick one next provider (owner's call - not QA's to prioritize) and follow the existing `Provider`
interface (`providers/base.py`) exactly, auditing the four existing providers side-by-side the way
`qa/knowledge/historical-risk-areas.md` recommends, since every real bug this project's QA cycle
found traced back to a new provider/kind not matching an existing sibling's shape (BUG-001,
BUG-005).

## Implementation (qa-developer, 2026-11-01)

**Source chosen: VATComply** (`api.vatcomply.com`, `madisvain/vatcomply`, ECB-sourced market mid
rate), as a new `/vatcomply` suffix alongside the existing `/boi` suffix, same `fx` kind, same
`Provider` interface - no new `InstrumentKind`, no config_flow/const.py/detectors/card wiring
beyond the fx provider's own existing per-source branches.

Why this one, over the alternatives researched: it mirrors Frankfurter's exact request/response
shape (`base`/`symbols`/`date` query params, `{"date","base","rates"}` JSON), so it is genuinely
redundant (a second, independently-hosted market-rate service to fall back on if Frankfurter is
down) rather than a different kind of data. `@fawazahmed0/currency-api` (jsdelivr/Cloudflare
Pages CDN) was also confirmed live and free/no-key, but was passed over since VATComply's shape is
closer to Frankfurter's (less code divergence) and its docs are a normal hosted API rather than an
npm-version-per-date CDN convention.

**Confirmed live, 2026-11-01**, against `https://www.vatcomply.com/api/exchange-rates/` and real
calls:
- `GET https://api.vatcomply.com/rates` - no key, anonymous rate limit 2 req/s per IP (per
  `https://www.vatcomply.com/rate-limiting/`).
- Params: `base` (default EUR), `symbols` (comma-separated), `date` (YYYY-MM-DD, historical;
  omitted = latest). Response: `{"date":"2026-10-30","base":"EUR","rates":{"ILS":3.91}}` -
  confirmed verbatim for both a latest call and a specific historical date
  (`?date=2026-10-20` returned real October 2026 rates).
- **No start/end range param**: a tried `start_date`/`end_date` pair was silently ignored by the
  live API (returned the latest rate instead, not an error) - confirmed live, not assumed. So
  `fetch_history()` for this source issues one dated request per day in the range, unlike
  Frankfurter's single `/{start}..{end}` call and BOI's single `startPeriod`/`endPeriod` call.
  Latest-rate lookup (`fetch_snapshot`-equivalent) and historical date lookup
  (`fetch_history`-equivalent) are both present, matching Frankfurter/BOI's capability - no
  regressed feature vs. the existing two sources.
