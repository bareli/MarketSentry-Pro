# UX-003 Daily digest blueprint produces a lopsided, hard-to-scan notification with realistic instrument names

| | |

| Type | UX ISSUE |
| Severity | MEDIUM |
| Status | OPEN |
| Issue | [#6](https://github.com/bareli/MarketSentry-Pro/issues/6) |
| Screen | `blueprints/automation/marketsentry/daily_digest.yaml`'s rendered notification body |
| Workflow | Owner reads the once-a-day consolidated digest notification instead of per-event alerts |
| Persona | The owner (Victor), reading a push/persistent notification, often on a phone |
| Viewport | N/A - notification text, code-review + hand-traced render (see *Evidence*) |

## Problem

The digest builds one line per tracked instrument as
`{{ s.attributes.friendly_name }}: {{ s.state }}{{ ' ' ~ s.attributes.unit_of_measurement if ... }}`,
using the entity's raw `state` (no thousands separator, no currency symbol) and its full HA
`friendly_name`. Because every MarketSentry Pro entity sets `_attr_has_entity_name = True`
(`custom_components/marketsentry/entity.py`), `friendly_name` is `"<device name> <entity name>"` -
and for a Polymarket outcome, the device name is the **entire market question**. With a realistic
mix of instrument kinds (the same mix already used in the project's own Playwright harness mock
data and the live smoke-tested owner dashboard), the digest reads like:

```
Will the Democratic Party control the Senate after the 2026 Midterm elections?: Yes Probability: 62.3 %
AAPL Inc Price: 150.52 USD
EUR/ILS (market rate) Rate: 3.9123 ILS
Bitcoin (BTC) Price: 67000.5 USD
```

## Why it matters

One line out of four is roughly 5x longer than the others, dominates a push notification's limited
visible area (most mobile notification UIs truncate well before "...2026 Midterm elections?: Yes
Probability: 62.3 %" finishes), and pushes the shorter, equally-important stock/crypto/FX lines out
of the glanceable area. The raw `67000.5` (no thousands separator) and `3.9123 ILS`/`62.3 %`
(inconsistent unit placement: space-prefixed unit vs. no unit) also read noticeably rougher than
the card's own `formatValue`/`formatCompactUsd` output the owner already sees on the dashboard
(`$67,000.50`), so the digest and the dashboard disagree stylistically for the same numbers. This
is exactly the "digest stays readable with a mix of kinds" question the plan calls out, and the
realistic data shows it does not, once a Polymarket question is in the mix.

## Evidence

The digest has never fired against live HA Jinja this session (`qa/CLAUDE.md` §1 gates triggering
blueprints on the owner's real instance), so this is not a live notification screenshot.
`Evidence unavailable` as a screenshot for that reason. The four-line example above is a hand
trace, not a Jinja engine run (no `jinja2` package available in this offline environment to render
`integration_entities`/`expand`/`selectattr` safely without stubbing HA internals) - it is built
directly from the template in `daily_digest.yaml` plus the project's own ground truth for what
`friendly_name`/`state`/`unit_of_measurement` would be for each kind:

- Outcome: `_attr_has_entity_name = True` + `translation_key = "probability"` (`sensor.py:75-81`,
  `en.json`'s `entity.sensor.probability.name = "Probability"`) → friendly_name is the full device
  name (the market question, as already shown verbatim in `card/e2e/harness.html`'s own mock data
  and matching the real market name used in the live BUG-001 reproduction) + " Probability";
  `_attr_native_unit_of_measurement = "%"` (`sensor.py:78`).
- Stock/crypto/FX: same `has_entity_name` pattern with `translation_key = "price"`/`"rate"`;
  `_attr_native_unit_of_measurement = tracker.ref.unit` (raw unit string, e.g. `"USD"`/`"ILS"`,
  `sensor.py:207`), state is `tracker`'s raw float, unformatted.

## Recommendation

Two independent changes, either one helps:

1. Use the **device** name (`s.attributes.friendly_name | regex_replace(' ' ~ s.name ~ '$', '')`
   is fragile; simpler: expose a `device_id`/device-name lookup, or just drop the per-entity
   suffix by templating off `device_attr(s.entity_id, "name")` instead of the entity's
   `friendly_name`) so the digest shows "Will the Democratic... Senate...?: Yes: 62.3 %" instead of
   repeating "... Probability" on every line - shorter, and consistent with how the card itself
   labels rows (device name only, kind implied by context).
2. For the outcome case specifically, consider truncating long market-question names in the digest
   (e.g. first 60 chars + "…") since Polymarket question text is the one kind of MarketSentry Pro
   instrument name with no natural length bound - stock tickers, FX pairs and coin names are all
   short by construction.

## Kind

`works, could be better` - the digest renders without error for any instrument mix; it's the
resulting text's readability, not correctness, that degrades with a realistic market-question name
in the mix.

## Prototype

Not offered - this is a Jinja template wording/formatting change inside a blueprint, not an
interface a prototype would usefully mock up.
